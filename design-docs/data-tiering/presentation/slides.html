Valkey Data Tiering

Transparent NVMe storage for cold items

Valkey Contributor Summit 2026 | Abhishek Kumar

What Problem are we solving?

Because Valkey stores all data in DRAM

  • Dataset size constrained by memory capacity
  • Costs scale linearly, ignoring access frequency
  • Evicted data must be repopulated from origin
  • Cold data pays the same DRAM rent as hot data
  • Limits Valkey adoption as a primary database for larger, skewed workloads
100% of data in DRAM
~$8/GB DRAM cost
~$0.08/GB NVMe cost

Who is the Customer?

Target Workloads

  • Large datasets with skewed access
  • Small portion of keyspace is hot
  • Session stores, catalogs, user profiles
  • Want cold data accessible without another store
  • Cost-conscious

Not Suited For

  • Uniform access patterns
  • Full-scan-heavy workloads
  • Tiny-value-only datasets
  • Highly rotating datasets
10-20% hot keys in typical workloads
80-90% cold data paying DRAM rent

What is the Proposed Solution?

Instead of evicting infrequently accessed data,
move it to NVMe and bring it back when needed.

Write Path

Client writes go to DRAM normally. Cold values are spilled asynchronously.

1Client SETnormal DRAM write
→
2Spill selectLRU/LFU sampling
→
3Submit robj*zero-copy handoff
→
4IO threadserialize + write
→
5Completionrelease RAM value

📝 Example

SET user:1001 "{name:Alice,...}" → writes to DRAM
user:1001 goes cold (LRU sampling picks it)
IO thread serializes → FlashCache writes to NVMe
DRAM value freed. Key stays. encoding=TIERED

Key points

  • Main thread hands off robj* directly. No serialization on main thread.
  • FlashCache: staging buffer write (sub-μs), sequential NVMe flush.
  • On completion: DRAM value released. Key stays in memory.

Read Path

Client hits a tiered key. Command is intercepted, value fetched, command re-executed.

1Client GETprocessCommand
→
2Intercept3-bit residency
→
3Block clientpause read handler
→
4IO threadread + deserialize
→
5Re-executeunblock + replay

📝 Example

GET user:1001 → key found, but encoding=TIERED
Client blocked (read handler disarmed). Others continue.
IO thread reads from FlashCache → deserializes → re-attaches
Client unblocked. GET re-executes. Returns "{name:Alice,...}"

Key points

  • Generic gate: one intercept for all commands. No per-command hooks.
  • Client is paused (not the engine). Other clients continue normally.
  • Multi-key commands: all tiered keys fetched before command runs.

Key State Machine

Every key has a 3-bit residency state. Six states, all transitions well-defined.

Which Storage Engine?

FlashCache vs RocksDB — identical hardware, 200M keys, 1KB values, 80/20 read/write

14.5x faster pure writes
1.5x write amplification
vs 25.6x RocksDB
10 μs flat write latency
(buffered log append)

FlashCache: log-structured, 1 thread, libaio. RocksDB: leveled compaction, 4-64 threads. Same NVMe.

V1 Scope

✅ V1 Ships

  • Whole-value tiering for all types
    (strings, hashes, lists, sets, zsets, streams, JSON, Bloom)
  • RDB, AOF, replication, failover, slot migration
  • LRU/LFU spill-before-evict
  • Promote-on-access, size-gated admission
  • Pluggable backend with FlashCache default
  • Async IO, throttling, backpressure, metrics

🔮 Deferred

  • Key-spilling (keys on flash)
  • Partial fetch / partial update
  • Search module integration
  • User-defined policies
  • Manual TIER / UNTIER commands

Architecture does not foreclose any of these.
